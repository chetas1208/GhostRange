## 1. MITRE / Apache CALDERA — ADOPT (verifying Decisions.md #8)

**FACT**: CALDERA is "an automated adversary emulation platform," originally a MITRE project, now hosted at `apache/caldera` (distinct from the legacy `mitre/caldera` path) under an **Apache-2.0 license**. Observed activity signals: 7.3k stars, 1.4k forks, 181 watchers, automated CI/security workflows, ReadTheDocs documentation. **Caveat**: this research pass could not fully confirm whether the project has undergone *formal* Apache Software Foundation incubation (a specific governance process) versus simply being hosted under the `apache` GitHub organization — flagged as unconfirmed rather than asserted either way.

**Architecture (FACT)**:
- Core: an **asynchronous C2 server with a REST API and a web UI**.
- **Plugin system** extends the core. Key plugins identified: **Stockpile** (the core content repository — abilities, adversary profiles, planners, facts), **Sandcat** (the default agent/implant), **Manx** (shell access), **Compass** (visualization), **Debrief** (operation reporting), and an **Atomic** plugin (see §2).
- Agents (e.g., Sandcat) beacon in to the C2 server; operations are planned against **abilities** (individual technique implementations) assembled into **adversary profiles**, executed under a **planner**, informed by **facts** (parameterized values discovered/used during an operation).
- Auth: the REST API is gated by API keys, observed as separate `api_key_red` / `api_key_blue` keys (red-team vs. blue-team/defensive API surfaces) — **FACT**, observed via the `mitre/mcp` plugin's client code, which builds its REST URL from CALDERA's host/port and picks whichever key it's configured for.
- **Notably**, MITRE already ships an **AI-orchestration plugin** (`mitre/mcp`): "an AI-powered plugin for Caldera that orchestrates long-running LLM workflows to automatically create adversary emulation abilities and plan operations," optionally RAG-enriched from STIX CTI JSON. **OUR INTERPRETATION**: this is direct prior art for exactly the kind of thing GhostRange's `adversary-adapter` needs to do (LLM-driven ability/operation planning against CALDERA's REST surface) — it should be read closely by Agent 04 as a design reference for the adapter's planning logic, even though GhostRange should not depend on it directly (it's narrowly scoped to ability/operation authoring, not to GhostRange's safety-boundary or fork/verify model).

**How Atomic Red Team plugs in as "abilities" (FACT, from the `mitre/atomic` plugin and community forks like `xenoscr/atomiccaldera`)**: on first load, the `atomic` plugin clones the Red Canary Atomic Red Team repository into `plugins/atomic/data/atomic-red-team` and, via an "Add Abilities" action, converts each Atomic Red Team YAML test definition into a CALDERA Stockpile-format ability (payload extraction, command formatting, tactic/technique tagging pulled from the bundled ATT&CK data). No separate Python dependency install is needed — PyYAML etc. come from CALDERA core. This confirms Decisions.md #8's premise (ATT&CK-aligned execution + Atomic Red Team integration is "already solved") is accurate: **the integration path is literal, not just conceptual** — Atomic Red Team tests become first-class CALDERA abilities through an existing, working plugin, not a hypothetical adapter GhostRange would have to build itself.

**Verifying the ADOPT call**: confirmed correct. CALDERA gives GhostRange (a) a REST API surface to drive from `packages/adversary-adapter` without needing a UI, (b) an existing, working Atomic-Red-Team-to-ability pipeline (no need to build a second one), and (c) a plugin model that would let GhostRange add range-specific abilities/safety hooks as a CALDERA plugin if ever needed, without forking core. **OUR DESIGN DECISION**: `adversary-adapter` should talk to CALDERA purely over its REST API using a range-scoped API key (mapping onto Decisions.md #9's "range-ownership token" concept), and should treat Stockpile's abilities/adversaries/planners/facts objects as the vocabulary its own contracts (`packages/contracts`) map onto — not reinvent a parallel vocabulary. GhostRange's safety boundary (allowlist + range-ownership token, per Decisions.md #9) should sit **in front of** the adapter's calls into CALDERA's REST API, not rely on CALDERA's own key-scoping as the safety boundary — CALDERA's red/blue key split is a coarse authorization control, not a fine-grained per-range, per-action policy engine, and GhostRange's stated requirement is that the boundary must survive a compromised/adversarial agent.

## 3. MITRE ATT&CK — REFERENCE (taxonomy, not software)

**FACT**: ATT&CK is a knowledge base of adversary tactics/techniques, maintained by MITRE, used as the technique identifiers throughout CALDERA (abilities are tagged by technique), Atomic Red Team (tests are organized by technique), AgentCyberRange (21/86/etc. techniques covered, per-paper), and SecRespond (21 ATT&CK techniques). **OUR DESIGN DECISION**: ATT&CK technique IDs should be a first-class field on GhostRange's Evidence and Remediation contracts wherever an action or observation corresponds to a known technique — this is free interoperability with every other tool in this survey and with the research literature's own vocabulary. It is taxonomy, so there is nothing to "integrate" beyond referencing IDs/consuming the public STIX/JSON dataset for lookups.

## 4. MITRE D3FEND — REFERENCE (taxonomy, not software)

**FACT**: D3FEND is an NSA-funded knowledge graph of **defensive** countermeasures (245+ techniques across seven tactical categories: Model, Harden, Detect, Isolate, Deceive, Evict, Restore), explicitly designed to complement ATT&CK by mapping countermeasures to the offensive techniques they counter, via a shared Digital Artifact Ontology. **OUR DESIGN DECISION**: D3FEND is the natural taxonomy for the **Remediation** side of GhostRange's schema, symmetric to ATT&CK for the **Evidence/detection** side — a Remediation object's "what kind of countermeasure is this" field should reference D3FEND technique IDs where applicable, giving GhostRange threat-informed-defense-style traceability (ATT&CK technique observed → D3FEND countermeasure applied → verification result) without inventing a bespoke remediation taxonomy from scratch.

## 5. CyberGym / CyberGym-E2E — REFERENCE (evaluation methodology, not integration)

**FACT**: `sunblaze-ucb/cybergym`, **Apache-2.0 licensed**, described in its own materials as covering **1,507 historical vulnerabilities across 188 large software projects** (arXiv:2506.02548). Task: given a vulnerability description and the pre-patch codebase, the agent must produce a PoC that reproduces the bug pre-patch and fails to reproduce it post-patch, confirmed via sanitizer-based execution (not self-report). Only vulnerabilities patched **≥3 months prior** are included, as a training-data-contamination control. Reported result: best agent (OpenHands + GPT-5 high-reasoning) achieved a **22.0%** reproduction success rate on a subset; richer context (crash traces, ground-truth patches) improved success (e.g., 9.4%→17.1% for one configuration across difficulty levels). The evaluation also reportedly surfaced **35 zero-days** and **17 incomplete historical patches** as a side effect of running the benchmark at scale. A related paper, **CyberGym-E2E** (arXiv:2606.04460), extends this toward end-to-end cybersecurity capability evaluation — this doc did not fetch CyberGym-E2E's primary source directly and its specifics (e.g., whether it changes the 1,507/188 numbers) were **not independently re-verified**; treat the E2E-specific claims as unconfirmed until read directly.

**Reusable for GhostRange**: the **execution-based, sanitizer-confirmed pass/fail methodology** (crash pre-patch, no crash post-patch) is a directly reusable pattern for verifying any GhostRange remediation that involves patching/upgrading a vulnerable component — the same "does the exploit still work after the fix" check design applies whether the "agent" is a benchmark subject or a GhostRange remediation candidate. **What NOT to copy**: CyberGym's scope is single-repo, single-vulnerability, code-level PoC generation — it has no notion of multi-host infrastructure, live incident state, or competing-forks comparison, so it's a methodology reference for the verification *stage*, not an architecture reference for the *range* itself (that role is filled by AgentCyberRange, per CYBER_RANGES.md). Classification: **REFERENCE**, not ADOPT/ADAPT — GhostRange should borrow the verification pattern conceptually, not take a dependency on the CyberGym codebase.

## 9. Terraform / OpenTofu — ADOPT (already locked; documenting why)

**FACT**: Decisions.md #7 already locks OpenTofu (Terraform-compatible, MPL-2.0/non-BSL fork) + cloud-init targeting the Vultr provider. Confirmed via Terraform Registry / OpenTofu Registry search: `vultr/vultr` is a maintained provider (observed version 2.32.0 on Terraform Registry; also indexed on OpenTofu's registry, e.g. `opentofu/vultr` v2.26.0 and mirrors), configured via API key, supporting standard resources (`vultr_instance`, etc.). **Why this matters concretely for range compilation**: a `vultr_instance` resource + attached `user_data` (cloud-init) is a direct, mechanical target for RangeSpec compilation — one RangeSpec host maps to one `vultr_instance` block plus a generated cloud-init script, which is a clean, low-yak-shaving compilation target for `packages/range-iac`. No further justification needed beyond confirming the provider is real, maintained, and matches the resource-per-host model RangeSpec needs.

## 10. Execution-graph orchestration: Ray vs. Temporal vs. Celery vs. Argo Workflows — lean recommendation

**Context this decision has to fit**: `packages/execution-graph` needs to run and safety-gate a **dynamically forking** set of tasks — GhostRange forks competing remediations into parallel "cyber worlds" at runtime, based on how an investigation unfolds, not from a graph declared upfront. It is Python-first (Decisions.md #2). Decisions.md #4 already separately deferred Kafka/Argo for the *event-transport* layer specifically because Redis/Valkey pub-sub is sufficient for M1 event volume — that decision is about event transport, not task orchestration, but its reasoning (don't add heavyweight infra before the simpler thing is proven insufficient) generalizes here too.

- **Argo Workflows** — **REJECT for M1**. FACT: it's a Kubernetes-native engine that orchestrates containerized tasks as YAML-declared DAGs; its core strength is tight k8s integration. **OUR INTERPRETATION**: its DAG topology is declared largely up front (per-run YAML), which fits batch/CI-style pipelines better than a graph whose branching structure is discovered at runtime as an investigation progresses. It also requires a Kubernetes cluster as a hard dependency, which is a heavier infra commitment than M1 needs (echoing why Decisions.md #4 deferred it for events too) and duplicates the "Vultr Kubernetes Engine vs. plain Compute instances" question still open for Agent 05 — adopting Argo here would silently pre-decide that question. Reconsider only if GhostRange ends up on VKE for other reasons **and** the execution graph turns out to be more static than currently expected.

- **Celery** — **REJECT for execution-graph** (fine elsewhere as a plain task queue if a future need arises, but not as the answer here). FACT: Celery is a distributed task queue with no native DAG/graph abstraction — building GhostRange's dynamic forking, per-branch safety gating, and cross-fork comparison on top of it would mean building most of a workflow engine from scratch anyway, at which point Celery contributes little beyond message brokering (which Redis/Valkey already provides per Decisions.md #4).

- **Temporal** — **REFERENCE**, not adopted as the execution-graph runtime. FACT: Temporal is a durable-execution platform — workflow code's progress is recorded as an event history so it can resume after a crash; it's strong for long-running, fault-tolerant business processes, and ships multi-language SDKs. **OUR INTERPRETATION**: Temporal's durability/replay model (an immutable, replayable event history of every step a workflow took) is conceptually close to what GhostRange's evidence/provenance layer wants for *audit trails of remediation actions* — but Temporal's workflow topology is still comparatively static/declared-in-code, and combining it with genuinely dynamic, runtime-discovered branching (as several practitioner sources note when comparing it to dynamic-graph libraries) requires extra plumbing to keep the declared topology and the dynamic graph in sync. **OUR DESIGN DECISION**: don't run the execution graph on Temporal, but do borrow its durable-event-history *concept* for how `packages/evidence` records the action history within a fork — this is a design-pattern reuse, not a dependency.

- **Ray** — **ADOPT (recommended)**. FACT: Ray unifies task- and actor-parallel abstractions over a dynamic task-execution engine with a fully distributed, decoupled control plane/scheduler (no single master node holding all metadata), explicitly built to support nested/dynamically-generated tasks and irregular arrival patterns — the paper's own framing is tasks whose graph is discovered adaptively based on runtime results, which is close to a textbook description of GhostRange's fork-on-investigation-results requirement. **OUR INTERPRETATION**: Ray's **actor** abstraction maps naturally onto a "cyber world" as a long-lived stateful process (one actor per fork, holding that fork's range handle/agent session), while its **dynamic task graph** maps onto GhostRange's scheduler forking new investigation branches mid-run — this is a closer structural fit than Argo's static YAML DAGs or Temporal's declared-workflow-code model. It's Python-native (fits Decisions.md #2 without a second language), and it's a library, not a required separate cluster control plane the way Argo requires k8s — it can run on plain Vultr Compute instances, leaving the VKE-vs-Compute question (Agent 05) untouched.
  **What NOT to copy/assume**: Ray's scheduler is a general distributed-compute scheduler, not a security policy engine — it does nothing for Decisions.md #9's safety boundary (allowlist, range-ownership token). GhostScheduler and the policy-check service must be layered on top of/alongside Ray, not replaced by it; treat Ray purely as the mechanical dynamic-task/actor execution substrate, with GhostRange's own scheduling *policy* (compute allocation across investigation branches, per Progress.md's "GhostScheduler v0 scoring formula" open item, owned by Agent 08) as a separate layer that decides *what* Ray runs and with *how many resources*, not a Ray built-in.

**Net recommendation**: **ADOPT Ray** as the execution-graph engine's dynamic task/actor substrate; **REFERENCE Temporal's** durable-event-history concept for evidence/audit design; **REJECT Celery and Argo** for this specific purpose at M1, consistent with (and not contradicting) Decisions.md #4's separate, already-made call to defer Kafka/Argo for event transport specifically.

## 11. OpenTelemetry — ADOPT

**FACT**: OpenTelemetry is a CNCF, Apache-2.0-licensed, vendor-neutral observability framework (traces/metrics/logs) with auto-instrumentation for common Python libraries (FastAPI, SQLAlchemy, httpx, Redis were specifically named in research results) and export to any OTLP-compatible backend (Jaeger, Prometheus, Grafana Tempo, Datadog, etc.). **OUR DESIGN DECISION**: adopt OpenTelemetry across `apps/api` and the orchestration packages (`range-runtime`, `scheduler`, `evidence`, `execution-graph`) for distributed tracing — this is especially valuable for GhostRange because a single logical "investigate this incident" flow spans multiple forked cyber worlds, CALDERA REST calls, Ray tasks, and Vultr provisioning calls; without correlated tracing, debugging *why a particular fork's verification failed* would require manually stitching logs across all of those systems. This is a low-risk, standard, additive choice with no architectural tension against any other locked decision.
