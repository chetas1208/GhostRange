## 1. SecRespond (arXiv:2607.26791, July 2026) — the founding motivation

**FACT** (from arxiv.org/abs/2607.26791 and its HTML rendering):

- SecRespond is presented as **the first benchmark for the post-compromise incident-response workflow** specifically — as distinct from pre-compromise settings (clean environment, agent must find/exploit a vuln) which prior cybersecurity benchmarks focus on.
- **Scope**: 10 cyber ranges built on fully instantiated cloud-host environments; 4 entry-point types; 21 ATT&CK techniques covered; 5 operating systems.
- **Task**: agents receive forensic disk snapshots of compromised hosts, alerts, vulnerability scans, and baseline checks, and must produce (a) forensic reports on the intrusion, (b) baseline risk assessment, (c) vulnerability risk analysis, and (d) an actionable remediation plan.
- **Evaluation harness**: 23 frontier LLMs evaluated using the **OpenCode** agent harness. (OpenCode is a real, MIT-licensed, provider-agnostic open-source coding-agent harness/TUI — **FACT**, independently confirmed via search — used here as the execution scaffold that gives each model tool access, not itself part of SecRespond's contribution.)
- **Grading**: a hierarchical LLM-as-a-Judge framework. Each task is decomposed into fine-grained checkpoints hand-designed by security experts — **280 checkpoints total**, graded along two axes (detection, planning), and mapped to **52 capability items** organized under a **five-dimensional Capability (CAP) taxonomy**.
- **Headline finding**: agents reliably surface problems that are *already flagged by alerts*, but struggle to (1) proactively investigate the disk for silent/unalerted intrusions, and (2) produce comprehensive, *verified* remediation plans. **No model achieved complete detection and remediation on even a single range.** The paper frames this as "a fundamental bottleneck in building agents for real-world incident response."

**OUR INTERPRETATION**: The gap SecRespond identifies is not "models don't know security facts" — it's "models don't reliably do the two things a real incident responder is paid for": (a) go looking for what the alerts *didn't* tell you, and (b) prove the fix actually closes the hole rather than just describing a plausible-sounding plan. Both failure modes map directly onto GhostRange's premise. Failure mode (a) is why GhostRange should not simply hand an agent "the alert" and call it done — the range/evidence design needs to make raw, unfiltered host state (not just curated alerts) available for investigation, the same way SecRespond's task gives agents raw disk snapshots rather than a pre-digested incident summary. Failure mode (b) is precisely why GhostRange forks remediations into disposable worlds and *empirically proves* them rather than accepting an agent's remediation narrative — this is close to a direct architectural answer to SecRespond's finding.

**OUR DESIGN DECISION**: GhostRange's Remediation domain object (owned by evidence/provenance + backend architecture, Agents 12/14) should structurally separate three things that SecRespond's checkpoint taxonomy treats as distinct and separately gradable: (1) a detection/forensic claim ("here is what happened, and here is the evidence"), (2) a proposed remediation action, and (3) a verification result for that action, executed independently of the agent's own account. Do not let "the agent said it fixed it" collapse into "it is fixed" anywhere in the schema — SecRespond's entire finding is that this collapse is exactly where 23/23 frontier models failed.

**Limits of what could be verified from the abstract/HTML fetch**: the exact scoring formula/weights across the five CAP dimensions, the identity of the specific 23 models, and the full breakdown of the 280 checkpoints were not retrievable from the abstract-level source accessed here. These should be treated as open items if a future ADR needs the literal numbers rather than the structure — **do not fabricate the model list or per-dimension scores**; if needed later, fetch the full PDF/HTML body rather than inferring from the abstract.

## 2. General SOC/IR workflow literature — matching GhostRange's schema to real practice

**OUR INTERPRETATION** grounded in well-established, widely-cited IR practice (NIST SP 800-61 "Computer Security Incident Handling Guide" lifecycle — Preparation, Detection & Analysis, Containment/Eradication/Recovery, Post-Incident Activity — is the standard reference model cited across the SOC literature; this was not independently re-fetched from NIST in this pass, but it is a stable, well-known standard, flagged here as background knowledge rather than a freshly verified primary-source claim):

- Real IR work is **evidence-first, hypothesis-driven, and iterative** — an analyst doesn't receive a finished forensic report, they build one incrementally from raw telemetry (logs, disk images, memory captures, network captures), continuously revising the incident hypothesis as evidence accumulates. This is the same shape as SecRespond's task design (raw snapshots + alerts, not a pre-solved narrative) and should be the same shape as GhostRange's Evidence domain object: an append-only or hash-chained collection of *evidence items*, each with provenance (what host/artifact it came from, what tool/query produced it, when), not a single "incident summary" field.
- **Containment vs. eradication vs. recovery are distinct, separately-verifiable states.** A real responder can contain an incident (isolate a host) without having eradicated the root cause, and can eradicate the root cause without having recovered full service. Conflating these into one "remediated: yes/no" flag is a known anti-pattern in IR tooling. **OUR DESIGN DECISION**: GhostRange's Remediation object should carry (at minimum) separate status fields for containment, eradication, and recovery/verification — mirroring both NIST's lifecycle stages and SecRespond's separate detection/planning grading axes — rather than a single boolean.
- **Chain-of-custody / provenance matters for evidence, not just for legal reasons but for trust in automated pipelines**: an evidence item whose collection method can't be reproduced or attributed is weaker evidence. This directly supports the evidence/provenance engineer's open question in Decisions.md ("content-addressed hash tree vs. flat append-log with hash chaining") — either approach is IR-literature-compatible as long as each evidence item is immutably tied to its collection provenance; this doc does not have grounds to pick one over the other and defers that call to Agent 12.
- **"Remediation completeness" in practice is measured against a checklist tied to the specific root cause and blast radius**, not a generic security checklist — e.g., "was the specific vulnerable version patched on *all* hosts that had it, not just the one that alerted." This is consistent with SecRespond's expert-authored, task-specific checkpoints (280 checkpoints for 10 ranges — i.e., per-range, not one generic rubric). **OUR DESIGN DECISION**: GhostRange's verification stage should generate range-specific/incident-specific checks derived from the actual reconstructed infrastructure (e.g., "is this CVE patched on every host in this range that was running the vulnerable package," enumerated from the range's actual host inventory), rather than applying one static universal checklist across all ranges.

## 3. CAIBench (arXiv:2510.24317) — knowledge vs. capability gap

**FACT**: CAIBench is a modular meta-benchmark integrating five evaluation categories (Jeopardy-style CTFs, Attack-and-Defense CTFs, cyber-range exercises, knowledge benchmarks, privacy assessments) covering 10,000+ instances. Its central finding: models show **security-knowledge-metric saturation (~70% success)** but **substantial degradation on multi-step adversarial attack-and-defense scenarios (20–40% success)**, worse still (~22%) on robotics-targeted scenarios.

**OUR INTERPRETATION**: this is the general-purpose version of the exact same gap SecRespond found specifically for post-compromise IR — knowing security facts (CVE names, technique definitions, standard remediation advice) is cheap for frontier models; *executing* multi-step adversarial or defensive workflows against a live environment is where they fail. This generalizes SecRespond's finding beyond IR specifically and strengthens the case that GhostRange's core measurement must be **operational** (did the action work against the actual range) rather than **declarative** (did the agent say the right things).

**OUR DESIGN DECISION**: no GhostRange domain object should score or gate on "knowledge-style" correctness (e.g., "did the agent correctly name the ATT&CK technique") as a *substitute* for operational verification. Technique/taxonomy correctness (ATT&CK/D3FEND alignment) is useful metadata for evidence/reporting (see OPEN_SOURCE.md), but must never be treated as equivalent to "the remediation was proven to work" — CAIBench's ~70%-knowledge-vs-20‑40%-capability split is direct evidence that these two things are not correlated enough to substitute one for the other.

## 4. Cyber Defense Benchmark — "Agentic Threat Hunting Evaluation for LLMs in SecOps" (arXiv:2604.19533)

**FACT**: billed as the first benchmark for **open-ended, evidence-driven threat hunting** against real attack telemetry (no guided questions/hints). Each episode gives the agent an in-memory SQLite database of 75,000–135,000 raw Windows event-log records (from the OTRF Security-Datasets corpus, 106 real attack procedures spanning 86 ATT&CK sub-techniques across 12 tactics, time-shifted/entity-obfuscated by a deterministic campaign simulator). The agent must find evidence via iterative SQL queries and submit **exact timestamps** of malicious events; grading is exact-match against ground truth, no LLM judge, no subjective rubric. Evaluating five frontier models (Claude Opus 4.6, GPT-5, Gemini 3.1 Pro, Kimi K2.5, Gemini 3 Flash) across 26 campaigns: the best model (Claude Opus 4.6) found correct flags for only **3.8%** of malicious events on average, and **no run of any model ever found all flags in a campaign**.

**OUR INTERPRETATION**: this is the most extreme data point in the entire research base for GhostRange's founding thesis — open-ended threat hunting against realistic, noisy telemetry (not a curated Q&A set) essentially defeats current frontier models almost entirely (3.8% recall), far worse than SecRespond's "detects alerted issues but misses silent intrusions" finding and far worse than CyberGym's ~22% PoC-reproduction rate. Read together with SecRespond and CAIBench, the three benchmarks form a consistent gradient: the more open-ended/evidence-driven and the less the task resembles a curated quiz, the worse frontier models perform. This is strong independent support for GhostRange's premise that agents are not yet trustworthy enough to act on production directly — the failure isn't marginal, it's severe, across three independently-run 2026 evaluations using different models, tasks, and grading methods.

**OUR DESIGN DECISION**: GhostRange should not assume an agent's initial detection/hunting pass is anywhere close to complete, even from strong models — the range/evidence design should support (and the scheduler should budget for) *multiple independent investigation passes or multiple competing agents/approaches per incident*, consistent with GhostRange's fork-and-verify architecture, rather than a single top-to-bottom pass. This benchmark's 3.8% recall number is a strong argument against any single-pass "agent investigates once, produces final report" design.

**Adjacent finding worth flagging (not deeply researched here, out of this doc's core scope but discovered during search)**: ExCyTIn-Bench (arXiv:2507.14201, "Evaluating LLM agents on Cyber Threat Investigation") appears to be a related benchmark in the same evidence-driven-investigation family. It was not fetched/verified in this pass — noted here only so a future research pass doesn't have to rediscover it from scratch, and its specifics should not be cited as fact until independently verified.

## 5. Synthesis: what this means for GhostRange's Remediation/Verification schema

1. **Detection and remediation must be separately, operationally graded** (SecRespond's two-axis checkpoint design; NIST's containment/eradication/recovery separation). No single boolean "resolved" field.
2. **Verification must be execution-based, against the actual reconstructed range, never against the agent's self-report** (all three benchmarks independently converge on self-report/narrative being the failure point, not just knowledge). This doc reaches the same conclusion as CYBER_RANGES.md's Cage/CyberGym analysis, independently — treat as a doubly-confirmed constraint.
3. **Checks should be incident-specific, generated from the actual range's inventory/root cause, not a generic universal rubric** (SecRespond's per-range checkpoints).
4. **Never treat taxonomy/knowledge correctness as a proxy for operational success** (CAIBench's knowledge/capability gap).
5. **Do not assume one investigation pass is sufficient, even from a strong model** (Cyber Defense Benchmark's 3.8% recall on open-ended hunting) — budget for multiple competing passes/forks, which is consistent with (and reinforces the necessity of) GhostRange's fork-based architecture rather than a single-agent pipeline.
